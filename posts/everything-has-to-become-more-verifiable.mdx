- And so you have to spend a lot of time spending, like learning what the source code actually does and understanding it and working with it for a very long time to understand what it does.
- And instead I want to offer a model for what I call invariant-driven development, which is slightly different and different from, I would say, test-driven development, where tests are a type of variant — invariant, sorry — and these can be represented as, like, definition parsers or something, or, like, schema represented in schema or something, where these are almost like formal systems, like verifiers, like Lean, where programming languages, I don’t think, will become verifiable Lean-like systems, but we have to bring more of that ideology into, like, regular programming languages and try to define things as the outcome first and as invariants first, and make that, like the API and the public top-level, like the thing that the humans actually interact with, be very clear about what the program actually does.
- So minimal amounts of, like, system information is required by the human to understand what the system actually does.
- And this kind of thing will create, like a contour or, like a shape within which a human is able to interact with the system, and also it benefits AI systems as well, because they are able to think through the system faster as well, where humans mostly care about what’s on the surface to make sure that it is correct, while AIs care about what the implementation details are.
- Like you have to think about whatever software you're building as a composition of various verifiable systems, where hierarchically each system is additionally verifiable.
- Like at each layer you are able to see what it is actually trying to prove rather than looking at its implementation details.

- That's what I want to go for here, rather than like a procedural way of building things.
- So this is more like concepts from functional programming and, like declarative programming and data-driven programming paradigms.
